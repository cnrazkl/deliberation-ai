- `runs` is the aggregate root. It stores owner/idempotency indexes, status, snapshot id, provider mode, bounded review-round count, member count, an encrypted immutable member-configuration snapshot, encrypted question/report envelopes, and event sequence.
- Migration `0023_peaceful_kylun.sql` adds `(owner_id, created_at, id)` for bounded newest-first history pages and stable keyset traversal. The listing decrypts only selected question envelopes; no new plaintext question or report column was added.
- `runs.risk_profile` freezes the owner-selected `standard|high` profile and participates in the request hash. `local_schedules.risk_profile` freezes the same choice for future occurrences. Migration `0021_foamy_wallop.sql` defaults historical rows to `standard` and checks both enum values. High-risk report control results remain inside the encrypted report; no sensitive content is added to plaintext event payloads.
- `runs.prompt_version` and `runs.prompt_fingerprint` record the first-round prompt contract and its SHA-256 digest. Migration `0022_elite_nextwave.sql` defaults historical versions to `council-v1` and leaves their fingerprint null; new runs always freeze both values. The digest covers rendered member strings and request settings, not raw image bytes. Full rendered prompt text stays transient in preflight and is reconstructed from encrypted run context at execution; it is not written as a new plaintext column.
- DA-072 saves `cross-review-v1` per-reviewer instructions, input, peer ids and text fingerprint inside the existing encrypted `runs.report_ciphertext` envelope after round 0. No schema migration or plaintext prompt field is added. Historical reports have no review-prompt plan; they are not reconstructed with current instructions.
- `run_events` is an ordered replay ledger keyed by run and sequence.
- `model_runs` stores member identity, explicit analyst/red-team role, round, encrypted raw/parsed analysis or review output, and normalized error code. A failed parse may have encrypted raw text and an error code while parsed output stays null; the matching failed-member detail also lives inside the encrypted run report. No migration was needed for this previously nullable raw field.
- `claims` and `claim_occurrences` preserve normalized disposition and encrypted source text while retaining provenance links. Each claim also stores its stable report-local id and explicit evidence state: `unsupported`, `model-supported`, `externally-verified`, `contradicted`, or `stale`.
- Each claim stores synthesis coverage as `included`, `omitted`, or `unresolved`; the encrypted report carries the same value so the complete coverage ledger survives restart.
- `council_templates` stores a local name, description, member count, and encrypted reusable 2–6 member configuration.
- `provider_connections` stores multiple independently addressed encrypted provider secrets per local owner plus non-secret provider family, starting model, optional base URL, endpoint preset, reasoning protocol, and structured-output mode. Owner/label is unique; runs and templates refer to connections by id. Editing metadata can preserve the existing encrypted secret. Migration `0025_nervous_talos.sql` adds a nullable `catalog_snapshot_ciphertext` for the latest bounded normalized model-list result and a monotonic `revision`; an edit increments the revision and clears the snapshot. A catalog result writes only when the revision read before the request still matches, so stale checks cannot attach to changed credentials or endpoints. This is one latest observation, not a history of per-model capabilities.
- `provider_operations` records each provider/model/member/round attempt, exact request fingerprint, outcome certainty, operator resolution, remote response id, usage, encrypted successful result, and encrypted normalized citation metadata. A known parse failure may store encrypted raw text with null parsed output so restart replay preserves the failure detail. `(run, member, round, attempt)` is unique so analysis and review receipts cannot collide and retry authorization never overwrites ambiguous history.
- `memory_entries` stores at most 20 owner-selected claim snapshots with encrypted content, source run/claim provenance, source type, and evidence state at capture time. Runs store a separate encrypted immutable snapshot of at most five selected entries plus a non-sensitive count.
- `evidence_sources` stores owner-scoped claim links; encrypted title, URL, note, and immutable excerpt fields; optional publication date; immutable server capture time; explicit support/contradiction/context relation; content-review status; freshness-review status; and freshness decision time. It retains both the database claim id and stable report-local claim id. Legacy rows may have no excerpt, while every new row requires one.
- `research_captures` stores at most five owner-initiated public-web snapshots per claim. Requested/final URLs, title and extracted plain text are context-bound encrypted. Content type, byte length, redirect count, SHA-256 digest, capture/review times, separate `unreviewed|accepted|rejected` state and optional promoted evidence-source id remain queryable. Promotion never skips the evidence source's own unreviewed content/freshness states.
- `runs.attachments_ciphertext` stores the optional immutable image/PDF array under run-bound encryption. Only the bounded attachment count is queryable. Names, MIME types, SHA-256 values, base64 bytes and extracted PDF text remain inside the ciphertext; the server re-extracts PDF text and requires an exact match before enqueue. Migration `0017_nifty_tomorrow_man.sql` adds this snapshot field and migration `0020_condemned_night_nurse.sql` widens its database check to `0..6`. The token and text previews are transient; only the version and fingerprint are persisted.
- `mcp_connections` stores encrypted loopback endpoint labels/addresses. `mcp_tool_results` stores encrypted arguments and bounded text results, a digest and the producing tool/connection. A run freezes at most three successful results in `runs.tool_context_ciphertext`; only the count is queryable. Migration `0018_sharp_sally_floyd.sql` adds these records and constraints.
- `local_schedules` stores encrypted names, questions and complete member snapshots plus cadence, paused/active status, next/last occurrence and the durable run link. New schedules always start paused. Migration `0019_rapid_the_spike.sql` adds the table and validation checks.
- The encrypted final report keeps analyst `sharedClaims`/`distinctClaims` and `redTeamChallenges` as separate projections while all occurrences retain their source member and role. New member results also retain a normalized agreement-source key; old encrypted reports derive it from their frozen member configuration at read time. No schema migration is needed.
- Each claim group already stores its member occurrences, per-occurrence `kind`, `disposition`, evidence state and synthesis coverage inside the encrypted report. Mixed `objection`/other-kind groups are classified as distinct at build and read time using these existing fields. Stable claim ids and annotations are not rewritten, so no new database column or migration is required.
- The encrypted report now also stores each owner-authored claim `scopeNote` (up to 500 characters) and up to 100 pairwise `claimRelations` with kind, explanatory note, direction and update time. One relation per unordered claim pair is kept; reversing the pair updates that relation. A derived `claimCoverage` audit compares every validated member claim with its report occurrence id and exact provenance fields. Historical reports acquire this audit when read. Scope and relation mutations rewrite the encrypted report and append only ids, enums or a boolean to `run_events`; they add no plaintext content column or migration.
- Evidence-state and synthesis-coverage mutations update the searchable claim row and encrypted final report atomically, increment the run version, and append a content-free event containing only claim id and the selected enum.
- pg-boss tables share the same PostgreSQL database so run creation and job enqueue commit atomically.
- `worker_heartbeats` records one instance id, start time, last heartbeat and optional stop time per local worker process. Migration `0024_mighty_mandrill.sql` adds it. Diagnostics combine freshness with a matching live PostgreSQL session; stale rows can remain after a crash or restore without being counted as ready. The table stores no prompt, credential, model response or run content.

Deprecated plaintext content columns remain temporarily for migration compatibility and contain only `[encrypted]`, hashes, or null after backfill. New writes never place sensitive content in them.

## Decision data

[ADR-0017](adr/0017-advisory-decision-evaluation.md) uses three separate tables, not extra council members or rounds. `decision_connections` stores owner-scoped labels, exact pinned model ids and context-bound encrypted TypeSafe API keys. `decision_assessments` retains owner/run/claim/source provenance, input report revision, encrypted immutable input and rubric snapshots, mode/status, requested and returned model versions, and encrypted typed results. Full probability distributions and optional provider confidence belong to the result; semantic `insufficient_evidence` remains distinct from operational failure or `not_assessed` in evaluation data.

`decision_operations` is unique by assessment, batch and increasing attempt, with request fingerprints, outcome certainty, encrypted successful results, usage and explicit retry/discard history. Snapshot publication checks cancellation and input freshness. Owner scoping and context-bound encryption apply to connections, assessments and operations. Cascading parent deletion provides the current local retention boundary. Existing provider-operation payloads and final council reports keep their current types. Migration `0014_bitter_dust.sql` adds these records and indexes; `0015_numerous_madame_masque.sql` adds research captures and `0016_seal_research_captures.sql` enforces their snapshot immutability.
