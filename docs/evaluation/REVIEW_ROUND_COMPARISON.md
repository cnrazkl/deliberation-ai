# Review-round comparison preparation

DA-076 prepares a local, read-only comparison of the selected 0/1/2/3 cross-review limits. It does **not** run models, spend provider credits, compute invoice cost, or claim that more review improves accuracy. The frozen source-inclusive questions come from `COUNCIL_EXTERNAL_SUITE.json`; changing that source creates a different plan version rather than silently reusing run ids.

`pnpm review-rounds:prepare` writes `.local/review-round-comparison/plan.json` once and refuses to overwrite it. Each case contains its exact question, source-suite and question digests, effective risk profile, eligible review counts, and empty run-id slots. The local lexical risk policy excludes the zero-round slot for high-risk cases. The current 40-case suite has 145 eligible slots, including 15 cases where zero review is forbidden. Running every slot would require real provider calls and is **not** part of preparation.

After comparable terminal runs exist, an operator can enter each run id in its exact question/round slot and run `pnpm review-rounds:status`. The command checks owner-scoped encrypted run snapshots, exact source-inclusive question, current first-round prompt fingerprint, fixed members/model/connection/reasoning settings, effective risk, no attachments/memory/tool context or web search, full member and review completion, saved review-prompt fingerprints and unchanged instructions for each member/round, one successful provider receipt per member and round, no retries or ambiguous attempts, and a single recorded execution interval. It reports execution milliseconds and provider-reported input/output tokens only when every attempt supplied those counters. Missing counts remain null. It rejects fake-mode runs and does not make a provider request. It never overwrites the plan.

The `pairingStatus` field describes only whether every eligible cell has a matching saved run. `accuracyStatus` stays `human_review_pending`. Connection ids and model names in the frozen settings cannot prove that a remote service kept the same backend version or price throughout the study; a real experiment must also record a time-bounded provider/model/version and price snapshot and control the run order. These provider token counters are not a bill or a hard budget.

DA-077 introduced optional `cross-review-v3` self-revision proposals. This original DA-076 inspector rejects runs with that option enabled: they use a different prompt/output protocol and need a separately frozen comparison plan with human judgments. No existing comparison cell may silently mix v1/v2 and v3 runs.

Most importantly, the current application keeps the canonical claim ledger derived from independent round 0; review rounds add inspectable peer assessments but do not revise that ledger or generate a new final free-form answer. Existing source-claim recall therefore cannot measure a change in final-answer accuracy across review counts. A future human-reviewed study must separately label whether each review identified, missed, or introduced material errors and disagreements; if self-revision/synthesis is added, it must evaluate that versioned output separately. No quality result can be inferred from higher agreement or from this technical pairing report.
