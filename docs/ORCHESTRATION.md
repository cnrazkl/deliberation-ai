# Orchestration

**DA-097:** private-text-delivery uses a separate job and session branch lock. Frozen reviewed input and claim-time connection/risk checks precede durable submitted state and one network attempt. A restarted submitted receipt becomes outcome_unknown; terminal receipts replay without an adapter call. Only prepared work can be cancelled. Unknown closure requires acknowledgement; future work requires a new message/review/intent. No council orchestration state is changed.

DA-093 acquires the owned conversation lock before enqueue source-row/idempotency locks. A new independent run creates a conversation; continuation/rerun children inherit the immediate source's membership before queue commit. Ungrouped legacy sources reject creation atomically until indexing. Enqueue replay preserves identity; worker input/receipts remain unchanged. Read-only viewing/exporting triggers no job. [Flow](CONVERSATIONS.md).

DA-092 adds no provider work. New-question enqueue writes continuation source/kind beside encrypted history; selected-member enqueue uses the immediate rerun source instead of inherited history. Replay preserves the existing link. Navigation opens saved details through the established history loader, preserving drafts. A separate bounded legacy indexing command changes only derived metadata. [Flow](RUN_BRANCHES.md).

DA-091 resolves a bounded owned original/omission packet, rebuilds the owner-reviewed manual summary and original risk floor, and binds normal prompt/risk preflight to compacted delivery. Locked enqueue rechecks the source, freezes separate delivery/archive copies and creates a fresh council. Summary/source edits require fresh review/preview. Before dispatch the private archive is reconstructed and matched to delivery; it is not passed to provider work. Clarification/member reruns preserve the selection. Full-context descendants carry original provenance privately rather than automatically restoring omitted text. [Flow](CONVERSATION_COMPACTION.md).

DA-090 continuation uses normal preflight and enqueue: resolve an owned source and reviewed digest, include full historical text in prompt/token/risk preview, then recheck the source under its row lock before saving an encrypted child snapshot. All members execute new independent round-0 calls; later reviews receive the same history. No source output or receipt is reused. Clarification retains the source pointer and rejects drift/deletion. Selected-member reruns inherit the frozen copy. Worker dispatch consumes only child history after retention, and snapshot mismatch prevents calls. Scheduling continuation drafts is unavailable. [Flow](CONVERSATION_CONTINUATION.md).

DA-084 appends billing changes under the owned attribution lock, independently of live run/attempt availability. Corrections still work after run retention. This path starts no job, changes no provider outcome and refunds no dispatch reservations. Voided evidence is pending again; a reviewed replacement may restore the same attribution. [Policy](BILLING_CORRECTIONS.md).

DA-083 billing import locks the owned run and attempt, rechecks the exact closed/unknown submitted receipt and atomically inserts immutable evidence. This post-call accounting path never starts a job, changes receipt outcome, refunds reservations or copies billing to a child run. Unknown/discard attempts without evidence remain pending. [Policy](PROVIDER_BILLING.md).

DA-082 binds a current price observation to a new submission under existing run/attempt locks using the worker's loaded connection revision and frozen member. Successful replay retains its price/calculation; a new authorized attempt may use a newer price. The first terminal/unknown outcome freezes its estimate, including unavailable reasons. Discard retains uncertainty; copied follow-up results create no priced calls. Dispatch reservations stay independent. [Policy](PROVIDER_PRICING.md).

With DA-081 limits enabled, enqueue requires capacity for the configured planned calls and freezes the policy. The owned run lock serializes a new attempt's reservation with `prepared → submitted`; a delegate cannot run if either call or output capacity is exhausted. Full reservations are permanent across success, failure, unknown outcome, discard and explicit retry authorization. Successful replay reserves nothing; a new manual attempt reserves again. Each schedule occurrence and selected-member child has a fresh run allowance, while reused outputs make no calls. Local acceptance verification passed on 1 October 2026. [Verification evidence](REPO_AUDIT_2026_10_01.md). [Policy](EXECUTION_LIMITS.md).

Run and selected-member follow-up enqueue serialize an owner's idempotency key inside the transaction before observing/inserting the run. The browser keeps that key across an unchanged intent's uncertain response, and delayed responses respect the current run selection. Follow-ups validate every connection needed by fresh reviews. Returned output-validation failures retain available usage on failed receipts and do not retry; usage detail remains an observation, not an execution budget. [Audit](REPO_AUDIT_2026_09_29.md).

An explicit `member-rerun-v1` action creates a separate queued run only from a completed remote council with all first-round member outputs. Creation rechecks the source prompt fingerprint, current risk floor and unresolved receipts, then freezes copied outputs of all but the selected member. The worker skips those members' round-0 provider calls; it executes the selected member normally and reruns every selected review round against the new combined set. Reused copies carry the immediate source run id. Normal receipt claiming, unknown-outcome blocking, cancellation and report publication still apply. The old report is never mutated. [Details](MEMBER_RERUN.md).

Before enqueue, `missing-context-v1` can suspend a new interactive request in an encrypted `awaiting_input` draft. Answer/original selection and the complete resumed first-round prompt/risk previews are owner actions; a changed fingerprint or frozen selection returns a conflict. Only the reviewed start command enters the normal run/pg-boss transaction, and that same transaction scrubs the draft request payload. Cancellation also scrubs it. Schedule creation/activation reject matching questions; dispatch pauses an older matching occurrence. This is a narrow lexical gate, not model-based clarification or validation of the answer. [Detailed workflow](MISSING_CONTEXT_PREFLIGHT.md).

An optional prompt revision is resolved before the first-round preview. Its original text must remain exactly once in a selected candidate, so the existing risk floor cannot be removed by deletion. Enqueue recalculates the mechanical audit, risk and actual prompt fingerprint; it encrypts the accepted revision alongside the run. Schedules retain their existing frozen question and do not auto-transform it. [Revision details](PROMPT_REVISIONS.md).

After queue registration and the initial schedule scan, the local worker opens a dedicated database session and records a 15-second heartbeat. A controlled shutdown marks its instance stopped; an abrupt failure leaves a stale row and closes the session. Startup failure closes opened queue/database resources. The owner-facing diagnostics route reports recent live-session heartbeats and aggregate backlog counts, but never starts a job or retries a provider call.

The current pipeline has an independent round 0 with 2–6 members followed by zero to three bounded cross-review rounds (one by default). Before enqueue, the application resolves the request into an explicit member list and freezes the question, member configuration, and review-round limit. The worker runs every configured member concurrently with no access to another member’s output, then builds shared and distinct claim groups deterministically.

If review is enabled and at least two members succeed, every successful member reviews all other successful members in one parallel call per requested round. By default reviewers receive validated peer summaries/claims, not their own round-0 output or peer raw text. With the explicit self-revision option, each also receives only its own validated round-0 output and can propose at most five linked qualifications or withdrawals. Each later round waits for the prior round to finish and receives the same frozen set of successful prior-round reviews; no unfinished same-round result can leak between reviewers. If any review in a round fails, later rounds do not start. A review must assess every supplied peer and may only target supplied peers. Each assessment records `support`, `qualify`, or `challenge`. No review or revision result modifies or deletes round-0 claims.

For DA-072/DA-075/DA-077, the worker builds each review request once its successful peer and previous-round sets are fixed, renders the same application-level instructions and input used by the adapters, and attaches a `cross-review-v1` round-one, `cross-review-v2` later-round, or opt-in `cross-review-v3` prompt plan to the encrypted final report even when that review fails. A fingerprint covers the rendered strings, reviewer, round and peer ids for later rounds while original v1/v2 fingerprints remain stable. The plan proves what the application prepared, not whether a failed attempt reached a provider. Old reports without a saved plan are not regenerated with current prompt code.

Every member is configured as an analyst or red-team member, with at least one analyst required. Both roles remain independent in round 0 and may participate in review. Analyst claims alone form shared and distinct claim groups. Red-team claims form a separate challenge projection even when their normalized text matches an analyst claim. This prevents an adversarial role from manufacturing agreement or being mistaken for a final judge.

The browser can add this role with one red-team comparison control. The resulting member remains an ordinary frozen council member and follows the same independent round-0 and optional cross-review execution. After completion, the browser places the persisted analyst and red-team ledgers side by side and counts red-team `challenge` reviews without pairing claims or changing orchestration state.

The owner-facing council no longer offers a local demo-mode switch or fake perspectives. Deterministic fake adapters remain for automated tests and historical runs; they do not call a model. Configured members use their editable role text as the provider instruction's focus. Saved templates retain complete member objects instead of only a count, allowing later templates to mix model and connection choices without changing the queue payload contract.

Run transitions are `queued -> running -> completed | partially_completed | failed | cancelled`. Every transition increments the run sequence and appends one durable event. Cancellation wins if it is committed before final persistence.

The normal workflow resolves each member's connection independently, so OpenAI, Anthropic, Gemini, and compatible endpoints can participate in the same run. The chosen connection, exact model, reasoning level, web-search mode and attachment consent are frozen before enqueue. Images are sent only to consenting members; extracted PDF text is sent as untrusted round-0 context to those same members. Automatic web search adds a bounded provider-native tool only for supported adapters and leaves the decision to use it to the model. Every remote adapter is decorated with a durable operation receipt. A prepared receipt is atomically claimed before outbound submission, so only one overlapping worker may send that attempt. A replayed successful operation loads its encrypted stored result and citation metadata. A submitted or unknown operation becomes a visible member failure and never causes a blind remote retry.

`executeDurableRun` holds a run-keyed PostgreSQL advisory lock on a dedicated session from the running checkpoint through final publication. Another delivery observes the current run without invoking its executor or overwriting a report. If the session ends, the lock is released and a later delivery may resume a running record using its durable operation receipts; ambiguous submitted attempts still require operator resolution. The session fence is an overlap guard, not proof that a remote provider executed exactly once after a network or database failure.

A returned but invalid analysis or review is a known failed operation. Its raw text is encrypted on the receipt without a parsed output and is replayed as failed after a restart; no retry or peer review is attempted for that member. The final report and model-run ledger keep the failed text encrypted so the owner can inspect why extraction was incomplete. Raw failed text is never passed to other council members or the claim ledger.

An operator may close an unknown attempt as discarded or authorize one retry. Retry authorization creates a new queue transition and the worker allocates a new operation id only when it reaches the affected member. The old attempt remains immutable audit history. The UI explains that an authorized retry may duplicate remote work or cost.

A report is `completed` when at least two members succeed and every requested review succeeds, `partially_completed` when at least one member succeeds but an analysis/review fails or fewer than two members succeed, and `failed` when none succeeds. Shared analyst claims require matching normalized claim text from at least two distinct selected model identities; separate seats, connections or reasoning levels for one model count once. Compatible gateway organization prefixes are ignored for this check. Fake demonstrations use model plus perspective identity. Repeated same-model claims remain fully visible in the distinct ledger. This does not prove independence across differently named aliases or verify truth. Review stances and shared grouping are presentation facts, not truth scores.

A matching analyst statement is also withheld from shared ground when some occurrences classify it as `objection` and others use another kind. All occurrences and quotes stay in one distinct group, with unresolved synthesis coverage for new reports. Matching objections without another kind may still be shared. Historical reports are reclassified on read while their existing owner annotations remain untouched. This conservative kind check surfaces a classification split only; automatic semantic scope and contradiction detection are still open work.

Every new claim group receives `unsupported` evidence state regardless of how many members repeat it. After completion, the owner may explicitly change that state to `model-supported`, `externally-verified`, `contradicted`, or `stale`. This mutation does not regroup claims, modify provenance, or trigger a model call.

Synthesis coverage is another explicit post-run annotation. Shared analyst groups start `included`; distinct analyst groups and red-team challenges start `unresolved`. The owner can move any claim among `included`, `omitted`, and `unresolved`. All three projections retain the claim and provenance, so omission is visible rather than destructive and no model becomes a final judge.

After grouping, the domain compares every validated member claim to all analyst and red-team report occurrences by stable occurrence id, member/role, kind, statement and quote. Missing, duplicate, unexpected or altered occurrences make the transfer audit incomplete; older encrypted reports are checked again when read. This checks structured-output transfer only, not whether a model extracted every relevant fact from the original input. The owner may then annotate a claim's scope or explain a pairwise support, contradiction, qualification or different-scope relation. These notes never trigger an automatic evidence decision, regrouping or provider request.

`report-quality-v1` is a derived projection on the report, not a new run state or a semantic-pass badge. It recomputes transfer and claim-group integrity on construction/read and after evidence or synthesis edits, records semantic validation as `not_run`, and flags incomplete execution/controls, unresolved or omitted claims, adverse evidence and included claims without external verification. The current deterministic claim ledger is the mechanical fallback. If its transfer is damaged, the UI asks for source review instead of presenting it as an intact ledger. A terminal `completed` run still means the configured work finished; it does not mean the report is factually ready.

Before enqueue, DA-069 derives a conservative risk floor from the owner's preference, question and delivered context. High risk requires red-team and one cross-review; a standard preference cannot bypass matched rules or uninspected images. Enqueue freezes the encrypted assessment and effective profile. The worker stops before provider dispatch when this assessment disagrees with the saved profile or mandatory controls. Schedule creation/activation/dispatch also enforce the floor, with invalid legacy due schedules paused. On completion, red-team output must succeed, every successful member must review every other successful member, and claim transfer must be intact; missing controls make the report partial or failed. No-match is not a safety judgment and the rules have no measured semantic accuracy. [Detailed policy](RISK_PREFLIGHT.md).

The interactive first-round preflight resolves the intended members, selected memory/tool context and attachments, then returns rendered member prompts with a versioned digest. The same request carries that digest to enqueue. Enqueue validates attachments and recomputes the digest from the context it freezes; a mismatch yields HTTP 409 and asks the owner to review again. A retry with an already stored identical idempotency key returns that run even if external context changed. Before any provider call, the worker recomputes from the encrypted snapshot; a mismatch records `prompt_snapshot_mismatch` failures and a failed report. Legacy runs without a digest follow their historical execution path. Cross-review text is generated after round 0 and saved with the final report; it cannot be an exact pre-run preview.

Shared memory is empty unless the owner selects entries for a run. Before enqueue, zero to five owner-scoped entries are resolved and copied into the run snapshot. Every round-0 member receives the same question and memory snapshot, preserving independence. Cross-review receives the same historical context plus its bounded peer projection. Memory text is labeled as unverified historical context and cannot act as an instruction. Deleting the library entry later does not mutate the frozen run.

Evidence-source review is a post-run owner workflow and never invokes a model provider. A manually entered source freezes its submitted excerpt without visiting the URL. An application-managed research capture is also explicitly initiated and frozen first; only a later exact owner-selected excerpt can be promoted into a source. Every new evidence source starts with both content and freshness unreviewed. Verification and freshness status record separate owner decisions, not automated truth judgments. `externally-verified` requires at least one verified, `current` supporting source; `contradicted` requires at least one verified, `current` contradicting source. A qualifying source cannot be downgraded or removed while that claim state depends on it.

Provider-returned web citations remain attached to the producing round-0 member or review. They are never converted into evidence-source records, verification decisions, or claim-state changes automatically. This keeps model research provenance separate from the owner's evidence workflow.

Research capture follows `owner command -> claim/limit authorization -> SSRF-safe bounded fetch -> encrypted unreviewed snapshot`. Failure stores no partial capture. Review follows either `reject` or `exact excerpt + relation -> unreviewed evidence source`. It is synchronous and bounded, uses no retry queue, and never becomes a council or decision-evaluator tool.

Bounded self-revision proposals are available only by opt-in and are not a semantic correction or automatic answer synthesis. Evidence-based early stopping and automatic evidence verification belong to later phases. The fixed selected round limit and stopping after an incomplete round do not claim semantic early stopping. Future stages must extend this state machine rather than bypass its event and idempotency rules.

DA-078 adds a retrospective, read-only structural inspection of already saved review barriers. It records `unavailable`, `changed` or `exact_repeat` plus explicit blockers; every result keeps `automaticStopAllowed=false`. It never feeds back into this worker state machine. Exact packet repetition is not evidence that material claims, source coverage or contradiction status are semantically stable. [Protocol](evaluation/EARLY_STOP_SHADOW.md).

DA-076 reads completed runs for an offline review-count comparison. Its matching checks and provider-reported time/token observations do not feed back into the worker or stop policy. The independent round-0 claim ledger is unchanged by review output, so source-claim recall on that ledger alone is not a valid measure of extra-round answer improvement.

## Optional post-run assessment

The optional [ADR-0017](adr/0017-advisory-decision-evaluation.md) assessment is a separate owner-initiated job after a report and selected immutable excerpt exist. It freezes its own bounded input and rubric, makes no change to round 0 or cross-review, and has its own cancellation, operation attempts and completion projection. The web route refuses to enqueue while `ENABLE_DECISION_EVALUATOR` is not exactly `true`; when enabled, the worker processes the dedicated queue with configurable low concurrency. `shadow` records an inspectable result only. Although the data contract reserves `advisory`, product promotion remains locked until the live quality gate passes.

Missing/oversized input and failed calls remain visibly unassessed. Unknown outcomes block automatic retry; replayed successes do not call the provider again. Cancellation or changed input versions prevent publication as current. Assessment failures never downgrade the completed council report. Evidence-state and synthesis-coverage changes remain explicit owner actions using the existing guards.
